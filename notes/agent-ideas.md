## 2026-04-29

### 闭环 Agent 的核心判断

真正有意义的 agent，不是一次性完成任务，而是能在真实环境的持续输入中形成闭环：

```text
输入 -> Agent 执行 -> 输出 -> Agent 复盘 -> 更新 Agent -> 下一次输入
```

其中“更新 Agent”不是只更新模型，而是更新整个系统：

```text
更新 Agent = 更新知识 + 调整模型使用方式 + 改造工具 + 加工数据
```

核心观点：

- 大模型是解释与决策主体。
- 知识是行动规范与方法来源。
- 数据是世界状态与价值载体。
- 工具是意图转化为现实动作的媒介。
- 反馈是经验转化为能力的机制。

一个可以在真实环境持续输入中不断迭代的 agent，才真正具备落地意义。

### 适合落地闭环 Agent 的场景筛选标准

适合尝试 agent 落地的场景，最好满足：

- 输入持续：每天都有新任务。
- 输入便宜：API、RSS 或内部系统可稳定获取。
- 输出明确：更偏分类、提取、判断、执行建议，而不是纯创意。
- 反馈可得：有采纳、关闭、得票、点击、回复、转化等信号。
- 风险可控：先做建议、草稿、标注，不直接执行高风险动作。
- 知识可沉淀：每次失败都能转化成规则、SOP 或工具改进。

优先候选：

- GitHub Issue/PR 分诊 Agent。
- SEC 公告/财报事件提取 Agent。
- Stack Overflow/技术问答分诊 Agent。
- HN/社区趋势侦测 Agent。
- arXiv/论文情报筛选 Agent。

## 2026-04-30

### 新领域知识建立：先重建人类活动，再生成假设

在不了解业务背景时，AI 不能直接“提取模式”。面对一堆文档、数据、图片等材料，如果没有方法论和结构，就会有无数归纳方向和假设。

更合理的顺序不是：

```text
材料 -> 提取模式 -> 生成知识
```

而是：

```text
材料
  -> 重建人类活动场景
  -> 识别对象、角色、目标、动作、约束、结果
  -> 形成案例卡片
  -> 比较案例之间的差异与共性
  -> 生成可证伪假设
  -> 验证后沉淀为知识
```

底层结构：

```text
人类做事 = 目标 + 情境 + 对象 + 判断 + 动作 + 工具 + 结果 + 评价
```

所以建立 agent 知识时，第一步不是总结 SOP，而是把材料还原成“人类活动单元”：

- 谁在做事？
- 为了什么做？
- 对什么对象做？
- 在什么约束下做？
- 通过什么工具做？
- 做的时候如何判断？
- 做完以后谁说它好或不好？

只有先形成活动模型，后面才有资格谈模式发现。

模式发现应该沿着稳定维度进行：

- 相同情境下，人类是否做出相似判断？
- 相同对象上，成功案例和失败案例差在哪里？
- 专家和新手的处理差异是什么？
- 正常流程和异常流程的分界在哪里？
- 哪些动作带来了更好的结果？
- 哪些信息缺失会阻断下一步？

生成的知识不应一开始就被当成规则，而应先被表达为可证伪假设。

例子：

```text
当 issue 声称是 bug，但缺少版本、复现步骤和实际输出时，
维护者通常不会直接判断 bug，而是先要求补充信息。
原因是：缺少这些信息无法复现，也无法分配责任模块。
可验证方式：查看历史 issue 中 needs-info 标签和维护者追问内容。
反例：如果错误日志已经明确指向已知模块，可以直接关联已有 issue。
```

知识建立的分层：

```text
原始材料：文档、图片、数据、聊天记录
事实重建：发生了什么
活动建模：人在什么目标下如何行动
模式发现：哪些行动反复出现
因果假设：为什么这样做有效
执行知识：agent 应该如何判断和行动
评估知识：如何知道它做得对不对
```

原则：

- 不先建知识库，先建活动模型。
- 不先写 SOP，先积累案例卡片。
- 不先找规则，先比较成功、失败、异常。
- 不先自动化，先理解人类判断点。
- 不先追求闭环，先定义什么反馈能说明知识有效。
- 不把 AI 输出当知识，只把它当假设。
- 知识必须经过任务验证，才从假设升级为规则。

核心判断：

> 新领域的 agent 知识不是从材料里“提取”出来的，而是通过重建人类活动、比较真实案例、生成可证伪假设，并在执行反馈中逐步验证出来的。
